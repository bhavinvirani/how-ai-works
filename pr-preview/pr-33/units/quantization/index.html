Most of those digits were never doing anything

Somebody is reading numbers down the phone to you and you are writing them down. There are four hundred of them.

The first one is 3.14159265358979. You get it down. The second is 2.71828182845905.

Twenty minutes in you notice something about the job. You are not adding these numbers up. You are not sorting them or comparing them or doing anything with them at all. You are receiving them and copying them out, and each one takes about fifteen seconds, because every one of them is fifteen digits long.

Ask for two decimal places instead and the best part of two hours becomes half an hour. Not because 3.14 is easier to think about than 3.14159265358979. Because there is less of it to say.

What is actually in the file

A model is a pile of dials, and a dial is a number. A small model by today’s standards has about seven billion of them, and the file you download is those seven billion numbers, one after another, and almost nothing else.

So the size of that file is not really a fact about how clever the model is. It is a fact about how many digits each of those numbers is written in.

Computers write numbers in binary digits — plain on-or-off switches, which is the only kind of mark the hardware has. Each switch you add doubles how many different values the number can take, and each one you take away halves it. Sixteen switches give a dial 65,536 possible values. Four give it sixteen.

Training is usually done at thirty-two switches per dial, and the model is usually served at sixteen — a halving so routine that nobody thinks of it as compression at all. Neither figure was picked because a dial needs that much detail. They are what the hardware and the arithmetic of training happened to make convenient.

Whether the model was ever using that detail is a different question, and it is the question of this unit.

Same dials, coarser ruler

Here is the operation, at the scale of one small handful of dials.

Take a group of them, a few hundred sitting next to each other in the file, and look at the range they cover, from the lowest to the highest. Now lay a ladder across that range with a fixed number of rungs on it, and move every dial in the group to the nearest rung.

The word for forcing something onto a fixed set of steps like that is quantization — from quantum, meaning a fixed portion rather than a smooth range. It is the same idea as a shop that sells eggs by the half-dozen: you can still buy roughly what you wanted, but not exactly, and the coarser the portions the further “roughly” gets from “exactly”.

Two things are worth pinning down before going further, because both are easy to get wrong.

Nothing is removed. Every dial that was in the model is still in the model, still connected to everything it was connected to, still doing its job. This is not a smaller model. It is the same model, written down less precisely.

And nothing is being compressed in the zip-file sense either. A zipped file has to be unzipped before anything can use it. A quantized model is used in the state it is stored in — the machine does its arithmetic on the coarse numbers directly, which is exactly why it also runs faster.

The half nobody expects

The size is the obvious win. The speed is not obvious at all, and it comes straight back to the person on the phone.

When a model writes one word, every dial it needs has to travel from where it is stored to where the arithmetic happens. That trip is slow. The arithmetic itself, once the numbers have arrived, is fast — modern hardware can multiply far more numbers per second than it can fetch. So for most of the time it spends writing a word, the machine is not computing. It is waiting for numbers to turn up.

Halve the length of every number and you halve what has to be carried, so a word arrives about twice as soon. That is why quantization is not a trade of speed for size. Both improve together, from the same change.

The last row of that picture is the honest limit. Keep cutting and the carrying eventually gets shorter than the sums, and from there on the machine is waiting on the arithmetic, which does not shrink at all. Shaving further stops buying anything long before you reach the bottom of what is possible.

Will it run on my machine

This is the question people actually arrive with, and it is one multiplication.

file size = how many dials × digits per dial ÷ 8

Count the dials, multiply by the number of binary digits you are spending on each one, and divide by eight, because eight binary digits make one byte.

Seven billion dials at sixteen digits each is 14 gigabytes — more than most laptops will give a single program, which is why a seven-billion-dial model has a reputation for not quite fitting. The same seven billion at four digits each is 3.5 gigabytes, which fits with room to spare.

Then add roughly a quarter on top for working memory, which is the part of the sum people leave out and then have to debug.

The part that does not shrink

Quantizing a model shrinks the model. It does nothing at all to the other thing sitting in memory while it runs.

Every conversation the model is holding needs its own working memory, kept for as long as the conversation lasts, and that memory grows with how much has been said. It is not made of dials, so cutting the digits per dial does not touch it.

Which produces a specific and very common surprise: a four-digit model that loads happily and answers short questions all day, and then falls over the first time somebody pastes in a long document. The model fitted. The conversation did not.

There are separate techniques for storing that working memory in fewer digits too, and they carry the same warning as everything else here — cheap at first, and then not.

Turn it down yourself

The panel below is a seven-billion-dial model with a dial of its own: how many binary digits to spend on each of them. Alongside the size and how much there is to carry, it reports five different things the model might be asked to do, each scored against what the sixteen-digit version managed.

Those five scores are not measurements of any real model — the panel says so underneath. Each one is worked out from two facts about the task, and both of them are things you have already met.

The first is how much room the model has at each decision. When it picks the next piece of text, the piece it picks is some distance ahead of the runner-up. On something it has seen a million times that lead is enormous. On something it barely knows, the second-best answer is almost level.

The second is how many of those decisions have to go the right way. A one-line reply needs one. A page of arithmetic needs every single one of them, because a chain is only as good as its weakest link.

Rounding the dials adds a small nudge to every one of those decisions. Everything in the panel follows from that.

Nothing has been rounded yet. Each dial has all 65,536 of its rungs to land on, the model takes 14 GB, and this is the row every setting below is measured against.

These five are not measurements of any real model. Each one is worked out from two things: how much room the right answer has at each decision, and how many decisions have to go right. That is enough to produce the shape — a long flat stretch, then a fall — and the order the abilities give way in. It is not enough to predict what any particular model will score, which is why the only number that settles anything is the one you measure on your own work.

The first thing to notice is how long nothing happens. From sixteen digits down to five, eleven of the fourteen steps on that slider, not one of the five rows drops below 97%, while the file goes from 14 GB to 4.4 GB and there is 3.2× less to carry. All of that detail really was spare.

Keep going. At four digits an everyday reply still scores 100%, and code that has to actually run has dropped to 83%. At three, code and arithmetic have both hit zero, and an everyday reply is still reading 95%.

Now switch on spend more digits where they matter and go back to four.

Two ways the damage is uneven, and both matter

That toggle is the first way. Some dials in a model are far more sensitive to being nudged than others, and which ones is something you can measure — run real text through it and watch which dials the answer is most sensitive to. Good quantization methods do exactly that, then leave the sensitive ones at a higher width and squeeze everything else harder. It costs about half a digit per dial in bookkeeping, so the file comes out slightly larger.

Watch what that buys. At four digits, code goes from 83% to 98%. At three, from zero to 85%. Half a digit of overhead is buying about one whole binary digit back everywhere else, which is why the four-digit builds people actually download are perfectly usable, while a flat four-digit rounding of the same model is noticeably not.

The second way is the one that costs people money, and three digits with the toggle on is where you can see it.

An everyday reply, 100%. Summarising a page you paste in, 99%. A fact it barely knows, 93%. Code that has to actually run, 85%. Twelve steps of arithmetic, 85%.

One model. One setting. Nothing on that list was quantized differently from anything else on it. The spread is entirely a fact about the tasks — how much room each decision had, and how many decisions had to survive.

And notice which end of the list is which. The row you would check first is the row that moves last. You would open this model, ask it a few things, hear exactly the model you know, and have no way whatever of finding out from that conversation that a seventh of its ability to write working code has gone.

Then take the last step down to two digits and watch the point become unarguable. An everyday reply is still at 92% — still fluent, still plausible, still sounding like itself. Code is at zero. Arithmetic is at zero. What survived is the manner, and the manner is the one thing you cannot judge it by.

Which is why the headline everybody repeats about quantization is true and almost useless. “Barely any quality loss” is a statement about an average, and an average across a mixed pile of tasks is precisely the measurement that cannot see any of this.

So what do you do with that

Three things follow, and they are the practical content of the unit.

Take the cheap part. Down to about four digits with a decent method is very nearly free — roughly a quarter of the size, 3.6× less to carry, and a model that is still the model. Not taking it costs real money for real nothing.

Do not go looking for the last digit. The stretch between four and two is not a continuation of the stretch between sixteen and four. It is a different kind of country, where each digit costs several times what the one before it cost, and the collapse arrives without a warning shot. There is a reason four digits is where nearly everybody stops.

Test the thing you actually do. Not somebody’s comparison table, and not a suite of typical questions — the specific work you are relying on this model for, scored end to end against the unquantized version on the same inputs. If what you are relying on is long, or rare, or has to be exactly right, you are in the part of the model that gives way first, and a general average will tell you everything is fine.

For developers
long   dials       = 7_000_000_000L;
double digitsEach  = 4 + 0.5;          // four, plus the bookkeeping
long   weights     = (long) (dials * digitsEach / 8);

long   working     = weights / 4;      // room for the conversation
boolean fits       = weights + working <= availableBytes();

The first three lines are the sum everybody does and the fourth is the one everybody forgets. weights is fixed the moment you pick a width; working is not — it grows with how much has been said, and it is not stored in four digits, so quantizing the model does nothing to it. A service that sizes itself on weights alone will load, pass its smoke test, and run out of memory the first time a customer pastes in a contract.

There is no Java-side quantization ecosystem worth pointing at. In practice the model arrives already quantized, in a file whose name says what was done to it, and your job is the arithmetic above plus an honest comparison against the unquantized build.

Checkpoint

A team swaps their support assistant for a four-digit build to halve the hosting bill. Their quality suite — four hundred real customer questions, scored automatically — comes back within half a point of the old numbers, so they ship it. Six weeks later the finance team reports that the assistant's invoice reconciliations have been wrong often enough to matter, and nobody can find a change that would explain it. Say what happened, and what would have caught it.

Show answerHide answer

Nothing about the half-point figure was wrong. Support questions are short and common: one or two decisions each, on ground the model has seen an enormous amount of, with the right answer a long way clear of the runner-up. Rounding the dials nudges decisions like that without shifting any of them off the right answer, so a suite made of them reports almost no change however hard the model has been squeezed.

Reconciliation is the other kind of work entirely. A dozen things have to be right in a row and one slip ruins the final number, so the same small nudge — the same model, the same rounding, nothing done differently to it — gets twelve chances to matter instead of one.

So the suite did not fail to measure carefully. It measured the tasks least capable of showing the problem, and then averaged across four hundred of them, which buries a fault in one kind of work under agreement about another.

What would have caught it is putting reconciliation in the suite and scoring it end to end — right or wrong on the final figure, not how similar the wording is — against the unquantized build on identical inputs. The question is never “is this model good”. It is “is this the same model”, and that only has an answer if something is being compared.

Worth carrying past this unit. Quantization does not wear a model down evenly. It takes bites out of particular things, and the things it bites are exactly the ones a casual check is worst at noticing, which means the reassurance you get from trying it out for five minutes is not weak evidence. It is evidence of the wrong thing.
